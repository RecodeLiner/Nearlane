# Windows Quick Share authorization - 2026-11-14

Historical static-analysis baseline. The subsequent local-only configuration import,
unauthenticated endpoint check and browser runtime are documented in
[oauth-runtime.md](oauth-runtime.md). Browser authorization was subsequently verified;
see [oauth-runtime.md](oauth-runtime.md).

## Key result

The official Windows payload contains a desktop browser OAuth implementation,
with loopback callback, authorization-code exchange, refresh-token support and
PKCE-related configuration. Therefore the Android gpsoauth/master-token approach
is not the only implementation direction worth investigating.

**This does not prove** the live client enables PKCE, that its OAuth client ID
can be reused, or that Google's servers grant either Nearby scope to an
independent developer's client. No Google login or token exchange was performed.

## Reproducible static evidence

Run `python3 tools/inspect_pe.py work/research/msi/NearbyShareExe` against the
matching payload. Safe evidence and PE file-offset to VA mappings are committed
in `windows-1.0.2757.0.indicators.json`; the binary/string dump is not.

| Observation | File offset (hex) | What it supports |
| --- | --- | --- |
| Google authorization endpoint | `2568748` | Browser authorization code path is present |
| Google token endpoint | `2568720` | Separate token exchange endpoint |
| `nearbysharing-pa` scope URL | `25687a0` | Narrow Nearby permission exists in this payload |
| `nearbysharingsdk` scope URL | `2568848` | A second, SDK-specific permission exists |
| Loopback redirect prefix | `26b5a30` | Local HTTP callback implementation |
| PKCE challenge-method parameter | `2683658` | PKCE-related URL construction code is present |
| PKCE verifier field | `262f5e0` | Verifier is part of token exchange data |
| Third-party OAuth config diagnostic | `24be1c8` | Code distinguishes first-party and caller-provided client configurations |

Additional configuration descriptors contain a `use_pkce` boolean with a false
default. A descriptor default does not establish the effective runtime value.
Diagnostics also mention validating state and checking the returned scope against
Nearby/SDK permissions. These are static strings, not proof the checks execute.

The app has a Flutter Windows library and Dart-facing exports including login,
logout and current-account operations. This suggests an existing UI/core seam,
but those Windows binaries are not reused by Nearlane.

## Original implementation added

`nearlane-auth` now contains a standard S256 authorization URL builder with
OS entropy, separate state, exact loopback callback validation, redacted secret
types, token form construction and bounded scope-checking of token responses.
It has no bundled Google client ID/secret, browser-cookie collection, embedded
sign-in window, master token, network adapter or credential persistence.

The CLI inspects a captured authorization URL from stdin and reports only
permission names, endpoint path, redirect type and presence of PKCE/state.
It does not retain or print the client ID or parameter secrets.

## What remains unknown / next decisive experiment

1. Determine whether an authorized independent OAuth desktop client can request
   `nearbysharing-pa` or `nearbysharingsdk`. The public scope catalog currently
   does not document these scopes; static third-party config support is not API
   provisioning or approval. Use a dedicated test account, not the main account.
2. Observe the live Windows login URL to confirm effective scopes, redirect,
   PKCE and consent. A local observation needs an environment capable of running
   the official app; that is not supplied by static analysis on this Linux host.
3. Implement HTTP exchange and OS storage only after the authorization boundary
   is understood. A successful ordinary Google sign-in without a granted Nearby
   scope must never enable Contacts in the UI.
4. Implement certificate publication/download and verify Contacts and OwnDevices
   separately against Android. An authenticated account is not yet an authenticated
   sharing device.

No claim of an authentication bypass, live Google access, Android interoperability
or a completed Quick Share implementation is made.
